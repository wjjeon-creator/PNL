# 7월 "수익성 개선 전략" 탭 신설

Status: Implemented

## 배경

- 7월 패널은 현재 3개 서브탭(수익성 요약 / 대리점 상세 / 상생 프로모션 충족률) 구조이며, 모두 원자료 실측값 기반이다.
- 사용자 요청: "계약 유형별로 어떤 계약 형태를 늘리는 게 좋은지, 실적/수익성 측면에서" 판단할 수 있는 4번째 탭을 추가하고 싶다.
- 이 프로젝트에는 2026-07-29에 "계약 유형별 상세" 탭이 "구조만 있고 결론이 약하다"는 이유로 삭제된 전례가 있다(커밋 `e2c6389`). 이번 탭은 같은 실수를 반복하지 않도록, 막연한 데이터 나열이 아니라 명확한 결론(어떤 유형에 집중할지)과 실행 가능한 계산 도구를 담는다.
- 브레인스토밍 중 사용자가 "채널세일즈팀이 대리점을 돌며 계약구조를 재설명하는 활동의 효과 측정"으로 방향을 바꿀지 잠시 고민했으나, 최종적으로 "어떤 계약 유형을 늘릴지"가 더 중요한 질문이라고 확정했다. 대리점 활성화 캠페인 효과 측정은 이번 스코프에서 제외한다(추후 별도 요청 시 재검토).

## 목표

7월 "대리점 상세" 탭 옆에 4번째 서브탭 "수익성 개선 전략"을 추가한다. 이미 계산되어 있는 `CONTRACT_TYPE_GROUPS_JUL`(계약유형별 대리점 수·설치수·순매출 합계·대리점당 평균)만 재사용하며, 새로운 원자료 파싱은 필요 없다.

## 비목표 (Out of scope)

- 채널세일즈팀의 대리점 재방문/재설명 활동 효과 측정 (별도 데이터 필요, 이번 스코프 아님)
- 8월 이후 순이익/ROI 추세 예측 (데이터 포인트가 6·7월 2개뿐이라 통계적 근거가 약함 — 사용자가 시나리오 계산기 방식을 선택하며 배제)
- 계약 유형별 "실적(설치수)" 자체의 예측 — 이 탭은 "이미 확보된 실적을 계약 유형별로 어떻게 배분하면 수익성이 좋아지는지"를 다루지, 전사 실적 총량을 늘리는 방법은 다루지 않는다
- 6월 탭에 동일 기능 소급 적용 — 이번 스코프는 7월만

## 섹션 구성

### 1) 핵심 콜아웃

`CONTRACT_TYPE_GROUPS_JUL`에서 대리점당 평균 순매출(`avg`) 기준 1위 유형과, 다른 유형 대비 배율을 렌더 타임에 계산해 문장으로 표시한다. 기존 `계약 유형별 수익성` 섹션의 `contractTypeInsight` 콜아웃과 같은 패턴(자동 계산, 하드코딩 금지).

표본 수가 작은 유형(예: (우수)위탁운영대리점 2곳)은 평균이 소수 대리점에 좌우되므로, 콜아웃에 표본 수를 함께 노출해 과대해석을 방지한다.

예시 (7월 데이터 기준, 실제 렌더링 시 재계산됨):
> "(우수)위탁운영대리점이 대리점당 평균 951만원으로 다른 유형 대비 최대 15배 높습니다. 다만 이 유형은 현재 2곳뿐이라 표본이 작다는 점은 감안해야 합니다."

### 2) 배경: 채널 실적 둔화 (위기감 컨텍스트)

외부 소스인 "2026년 채널세일즈 대시보드" 구글시트(`https://docs.google.com/spreadsheets/d/1eaL8EU0DkwaacEfjr86hIx20UVawgbwDVx2n307Vd1E/edit?gid=220365718#gid=220365718`)에서 확인한 수치를 **하드코딩된 한 문장**으로 인용한다. 이 시트는 PNL 프로젝트의 데이터 파이프라인에 포함되지 않으므로 링크만 걸고 값은 그대로 타이핑한다(라이브 연동 없음).

인용 범위는 보수적으로 정한다:
- 협력대리점 채널의 **완료된 달**(1~7월)만 사용 — 8월은 오늘(2026-08-11) 기준 11/31일치만 반영된 값이라 인용하지 않는다.
- 딜러사 채널은 등락이 커서(42%→23%→95%) 깔끔한 하락 추세로 보기 어려우므로 인용하지 않는다.
- 문구: "회사 전체 협력대리점 채널의 월별 목표 대비 설치 달성률도 연초 100% 안팎에서 7월 83%로 낮아진 상태입니다. 신규 대리점 확보 여력이 줄어드는 만큼, 확보한다면 수익성 높은 유형에 집중하는 편이 효율적입니다."
- 문장 아래에 기존 `sheet-link` 패턴으로 원본 시트 링크를 노출한다.

### 3) 계약 유형 확대 시나리오 계산기 (인터랙티브)

**입력**: 계약 유형 4종 중 하나를 고르는 `<select>` + 늘릴 대리점 수를 입력하는 `<input type="number" min="1">`.

**계산**: `예상 순매출 증가 = 선택 유형의 대리점당 평균 순매출(avg) × 입력한 대리점 수`. `input`/`change` 이벤트에서 즉시 재계산해 결과 영역을 갱신한다(별도 빌드/새로고침 불필요).

**표시 항목**:
- 선택한 유형의 현재 대리점 수·설치수·순매출 합계·대리점당 평균 (계산 근거로 노출)
- 예상 순매출 증가액
- 시나리오 적용 전/후 비교 막대 차트 — 기존 `groupedBar()` 헬퍼를 재사용해 "현재 순매출 합계" vs "시나리오 적용 후 순매출 합계(현재 + 증가분)" 두 막대로 표시

**주의 문구**: "대리점당 평균은 실측 데이터 기반이지만, 표본이 적은 유형((우수)위탁운영 2곳, (우수)협력 3곳, 일반위탁 4곳)의 신규 대리점 성과는 이 평균과 다를 수 있습니다."

## 데이터 흐름

```
CONTRACT_TYPE_JUL (기존, p·type·net 포함)
        │
        ▼
groupByContractType() (기존 함수, 변경 없음)
        │
        ▼
CONTRACT_TYPE_GROUPS_JUL { type, count, installs, sum, avg, share }
        │
        ├─→ 섹션 1 콜아웃 (avg 기준 정렬 + 배율 계산)
        └─→ 섹션 3 계산기 (select로 그룹 선택 → avg × 입력값)
```

새 JS 함수 2개만 추가한다:
- `renderStrategyInsightJul()` — 섹션 1 콜아웃 렌더
- `renderScenarioCalculatorJul()` — 섹션 3 계산기 초기 렌더 + input 이벤트 리스너 등록

새 `BUILDERS` 엔트리 1개: `chartScenarioJul` (그룹 막대 차트, `buildVisibleCharts()`가 처음 노출될 때 렌더 — 단, 이 차트는 계산기 입력값이 바뀔 때마다 데이터가 바뀌므로 기존 lazy-init 패턴과 별개로, input 이벤트 핸들러 안에서 `chart.data.datasets[...].data` 갱신 + `chart.update()` 호출 방식으로 처리한다).

## 검증 계획

- `node scripts/verify-july-data.cjs` 통과 확인 (이 탭은 새 `*_JUL` 데이터 상수를 추가하지 않으므로 기존 검증 로직 변경 없음)
